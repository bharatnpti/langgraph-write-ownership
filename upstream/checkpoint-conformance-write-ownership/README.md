# WRITE_OWNERSHIP — an extended capability for `langgraph-checkpoint-conformance`

**Status: offered upstream on 2026-09-01, and correctly not yet a PR.** The proposal is
[live on the LangChain forum](https://forum.langchain.com/t/a-checkpointer-that-accepts-two-concurrent-writers-still-scores-conformance-level-full/4460),
and was **answered on 2026-09-02** by a "LangChain Expert" who called it a real gap, agreed the
extended capability is additive because the suite already auto-detects optional capabilities, and
asked for a GitHub issue.

**No fork exists, no issue is open, and no PR has been raised** — that is the required order, not an
oversight. `require_issue_link.yml` auto-closes external PRs whose author is not *assigned* to a
linked issue, and only a maintainer can assign; the forum replier is a community contributor rather
than a committer. So the sequence is forum → issue → get assigned by a maintainer → only then a PR,
and it has advanced exactly one step. This directory is the finished artifact the post points at.

---

## The one-paragraph version

`libs/checkpoint-conformance` cannot detect a saver that lets any number of workers write
the same `thread_id`. Every one of its clauses is single-instance, sequential and
single-writer — 89 across 9 capabilities at `main`, 81 across 8 in the published 0.0.2 —
so a deliberately fence-hostile saver scores `conformance_level = FULL`.
This adds one **extended** capability, `write_ownership`, which fails such a saver: a
checkpointer that advertises write ownership must observably refuse a write from a
superseded owner. It is purely additive — no base-class change, no runtime change, no
existing saver affected or reclassified.

## The contract

Two parts, and the second is the one worth arguing about.

1. **Durability.** A write from a superseded owner must not become durable.
2. **Observability, by a stated deadline.** The superseded owner must be able to learn it
   lost — either the write raises, or an explicit `acheck_write_ownership()` barrier
   raises. Returning normally with no barrier is a *silent* refusal and fails.

Detection is override-based on `aclaim_write_ownership`, a method
`BaseCheckpointSaver` does not define. `capabilities._is_overridden` returns `True` for a
method absent from the base class (`if base is None or impl is None: return impl is not
None`), so the capability is auto-detected purely by a saver defining it. That is what
removes the blast-radius objection: nothing existing changes shape.

It must be **extended, never base** — `tests/test_validate_memory.py` asserts
`passed_all_base()` against `InMemorySaver`, so a base clause turns upstream CI red on
contact.

Rejections are recognised by a duck-typed marker attribute
(`is_stale_write_owner_error = True`) rather than by `isinstance`. Requiring the canonical
exception class would make a *test* package a runtime dependency of every conforming
saver, which is backwards. `StaleWriteOwnerError` ships as the canonical implementation
for anyone who wants it; a saver is equally free to mark an exception of its own. This
repository does the latter — `durable_agents.errors.RunLost` carries the attribute and
imports nothing.

Full reasoning, including why the refusal is *allowed* to be deferred, is the module
docstring of `tree/langgraph/checkpoint/conformance/ownership.py`.

### Three things it is not

- **Not serialization.** Ownership answers *who* may write, not in what order. An
  unfenced deployment must behave exactly as it does today, which is why the capability is
  opt-in and extended.
- **Not idempotency.** `test_put_writes_idempotent` stays correct.
  `test_duplicate_put_writes_from_current_owner_is_not_a_rejection` pins the two axes
  apart, so a saver that conflated them — turning every legitimate retry into a lost run —
  fails.
- **Not silent.** The nearest prior art upstream short-circuits stale writes and returns
  normally. `SilentInMemorySaver` in the self-test is that design, and it fails. See below.

## The verdicts

Full output: [`verdict.out`](verdict.out). 15 clauses.

**In memory** — no database, no network, so upstream CI can run all of it:

| Saver | Verdict | Why it is in the suite |
|---|---|---|
| `OwnedInMemorySaver` | **PASS**, 15 of 15 | Reference implementation, ~40 lines over `InMemorySaver`. Shows the contract is small, and gives CI a green fixture. |
| `HostileInMemorySaver` | **FAIL**, 7 of 15 | Advertises the capability, enforces nothing. The clause has teeth. |
| `SilentInMemorySaver` | **FAIL**, 7 of 15 | Genuinely refuses; never says so. The contested case, as a test. |
| `DeferredInMemorySaver` | **PASS**, 15 of 15 | Refuses, reports only at the barrier. Proves the second deadline is real. |
| `InMemorySaver` | capability **NOT DETECTED**, base intact, `FULL` | Nothing existing is reclassified. |

The seven passing clauses on the hostile saver are the interesting half: this capability
is about *transferring* ownership, so a saver that refused every write, or scoped
ownership to the whole process, would fail clauses a hostile saver passes.

**Against PostgreSQL 16.2** — the published saver, a fenced saver, and that same saver with the
fence removed. Counts are given both ways, because "7 of 15" is ambiguous on its own:

| Saver | Verdict |
|---|---|
| `AsyncPostgresSaver` 3.1.2, unmodified (advertising only) | **FAIL** — 7 passed, **8 failed** |
| a fenced Postgres saver | **PASS** — 15 passed, 0 failed |
| that saver with the **fence removed**, bookkeeping intact | **FAIL** — 10 passed, **5 failed** |

> The last two rows come from a separate project that is **not in this repository**, so they are
> reported here rather than reproducible here. `verdict.py` skips that half cleanly. Nothing in the
> proposal depends on them: the capability's own verdicts, including a reference implementation and
> a saver that ignores supersession, run in memory and are reproducible from this repository alone.

That third row is the one that makes the second row mean anything. Our implementation has
two independent halves — a SQL fence on every write, and the bookkeeping that turns a
refusal into something a caller can see. Removing only the fence leaves the observability
clauses passing and fails exactly five: the four durability clauses plus
`stays_superseded`. That is what the fence, and only the fence, buys. (Phase 1 of this
project already got caught by the inverse mistake once: a mutated client-side guard passed
7 of 8 state assertions while being unsafe in general.)

### A finding that fell out of writing this

Two clauses test the *same* collision — same checkpoint, same `task_id`, both owners —
differing only in the channel, and they behave differently:

- `test_superseded_owner_cannot_displace_the_current_owners_write` (ordinary channel) —
  passes even with the fence removed.
- `test_superseded_owner_cannot_displace_a_special_channel_write` (`__resume__`) — fails.

`aput_writes` selects `UPSERT_CHECKPOINT_WRITES_SQL` (`ON CONFLICT … DO UPDATE`) when
every channel in the batch is in `WRITES_IDX_MAP`, and `INSERT_…` (`DO NOTHING`)
otherwise. So on an ordinary channel a stale write is dropped by first-writer-wins —
accidentally safe for the surviving *value*, which is why
[`../../proof/`](../../proof/README.md) describes the damage there as annihilation of the
loser's write plus a forked chain, not displacement. On `__error__`, `__scheduled__`,
`__interrupt__` and `__resume__` it is last-writer-wins, and a superseded owner
**overwrites live data**. `__resume__` carries the answer a human gave to an interrupt.

Neither the fork nor this had a clause before; both do now.

## Why both a script and patches

The suite gains capabilities — `delta_channel_history` landed after 0.0.2 was published —
and all four modified files are lists that grew. A patch pinned to one revision goes stale
on contact with the next, and the conflict lands in exactly the enum-and-dict boilerplate
where a hand resolution silently drops an entry. `apply.py` expresses each edit as *append
to the end of the relevant block*, which survives that, and is idempotent so it can be
re-run after a rebase.

The two patches are generated from it and both verified to apply with `-p1`. The 0.0.2
patch deliberately does **not** apply to main; that divergence is the whole reason there
are two.

## What is not established

- **No real multi-machine partition.** Every verdict here is one host. The PostgreSQL half
  is one process with several connections; the reproduction this capability is derived
  from ([`../../proof/`](../../proof/README.md)) is two OS processes and `SIGSTOP`.
- **Sync savers are not covered, and cannot be.** The suite is async-only — measured:
  `PostgresSaver` overrides none of `aput`, `aput_writes`, `aget_tuple`, `alist`,
  `adelete_thread`, so all five land on `BaseCheckpointSaver`'s `NotImplementedError`.
  Validating this library therefore exercises `FencedAsyncPostgresSaver`, which our own
  strict mode still **refuses** at startup for want of an async canary. Conformance is not
  that canary: it asks whether a superseded owner is refused, the canary asks whether the
  private seam we hook is still where we think it is.
- **Pinned, like every verdict in this repository.** `langgraph-checkpoint-conformance`
  0.0.2 and main @ 2026-08-30; `langgraph-checkpoint-postgres` 3.1.2; PostgreSQL 16.2. A
  verdict here says nothing about any other version.
- **Nothing about whether upstream wants this.** The prior on that is not good and is
  written down honestly in
  the upstream landscape survey:
  zero external contributions have ever landed in `checkpoint-conformance`. Track B does
  not depend on the answer (ADR-0009).
